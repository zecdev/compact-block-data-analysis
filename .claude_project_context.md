# Claude Project Context - Compact Block Analyzer

## Project Overview

**Purpose**: Analyze bandwidth impact of adding transparent transaction data to Zcash's compact block protocol

**Key Goal**: Determine if adding `CompactTxIn` and `TxOut` fields should be:
- Part of the default `GetBlockRange` RPC method
- A separate opt-in method
- Controlled via pool-based filtering

**Status**: Analysis tool - used for protocol design decisions, not production code

## Related Protocol Changes

1. **lightwallet-protocol PR #1**: https://github.com/zcash/lightwallet-protocol/pull/1
   - Adds `CompactTxIn` and `TxOut` to `compact_formats.proto`
   - Extends `CompactTx` message with transparent data

2. **librustzcash PR #1781**: https://github.com/zcash/librustzcash/pull/1781
   - Implements pool filtering for clients
   - Allows selective request of transparent/shielded data

## Architecture

### Design Philosophy
**Hybrid approach**: Fetch real data + estimate additions
- Get actual compact blocks from lightwalletd (production baseline)
- Get full blocks from Zebrad (source of transparent data)
- Calculate protobuf overhead for new fields (accurate estimation)

### Why This Approach?
- **Accurate baseline**: Real compact blocks, not simulated
- **Simple**: Don't reimplement compact block generation
- **Fast**: Only need to estimate the delta, not rebuild everything

## Technical Details

### Protobuf Structure (from PR #1)

```protobuf
message OutPoint {
    bytes txid = 1;      // 32 bytes
    uint32 index = 2;    // output index
}

message CompactTxIn {
    OutPoint prevout = 1;
}

message TxOut {
    uint32 value = 1;         // zatoshis (not uint64!)
    bytes scriptPubKey = 2;   // variable length
}

// Added to CompactTx:
repeated CompactTxIn vin = 7;
repeated TxOut vout = 8;
```

### Size Estimation Logic

**Key considerations**:
1. Protobuf uses varint encoding for numbers
2. Bytes fields need: tag (1) + length (varint) + data
3. Nested messages need: tag (1) + length (varint) + message
4. Repeated fields: separate tag+length for each entry

**Critical details**:
- `TxOut.value` is `uint32`, NOT `uint64` or `int64`
- `CompactTxIn` contains nested `OutPoint` (not flat fields)
- No `sequence` or `script_sig` in `CompactTxIn` (differs from full tx format)
- No `n` field in `TxOut` (it's implicit by position in the repeated field)

### Data Sources

**Lightwalletd (gRPC)**:
- Protocol: gRPC over HTTP/2
- Default port: 9067
- Method: `CompactTxStreamer.GetBlockRange`
- Returns: Stream of `CompactBlock` messages
- Purpose: Get actual current compact block sizes

**Zebrad (JSON-RPC)**:
- Protocol: JSON-RPC over HTTP
- Default port: 8232
- Method: `getblock` with verbosity=2
- Returns: Full block with all transaction details
- Purpose: Get transparent input/output data for estimation

## Common Pitfalls

### What NOT to do:
1. ❌ Don't try to rebuild compact blocks from scratch
2. ❌ Don't assume `TxOut.value` is 64-bit (it's 32-bit uint)
3. ❌ Don't include fields not in the proto (like `sequence` in `CompactTxIn`)
4. ❌ Don't forget protobuf overhead (tags, length prefixes, nesting)

### What TO do:
1. ✅ Fetch real compact blocks from lightwalletd
2. ✅ Use actual protobuf encoding rules for estimation
3. ✅ Test with diverse block ranges (different eras, usage patterns)
4. ✅ Consider worst-case scenarios (blocks with heavy transparent usage)

## Testing Strategy

### Recommended Block Ranges

**Recent blocks** (~2.4M height):
- Most relevant for current usage
- Reflects modern transaction patterns

- Heavy shielded usage

## Decision Criteria

### Thresholds (suggested)
- **< 20%**: Consider default inclusion
  - Low impact on bandwidth
  - Simplifies API
  - Better feature parity

- **20-50%**: Consider opt-in method
  - Significant overhead
  - Client choice important
  - Pool filtering valuable

- **> 50%**: Likely separate method
  - Major bandwidth impact
  - Critical for mobile/limited bandwidth
  - Clear opt-in needed

### Factors to Consider
- Mobile data costs
- Initial sync time
- Daily sync bandwidth
- Server scaling (more data per client)
- Backward compatibility
- API complexity

## Important Notes

### About Zcash Block Structure
- Zcash has multiple transaction pools: Transparent, Sapling, Orchard
- Coinbase inputs have no `txid` (they're not spending outputs)
- scriptPubKey can be 25 bytes (P2PKH) to much larger (P2SH, custom)
- Typical transparent output: ~35-40 bytes in compact format
- Typical transparent input: ~40-45 bytes in compact format

### About Compact Blocks
- Purpose: Minimize bandwidth for light clients
- Contains: Block metadata + minimal tx data for wallet scanning
- Current: Shielded outputs/actions only (Sapling, Orchard)
- Proposed: Add transparent inputs/outputs
- Trade-off: Bandwidth vs. functionality
